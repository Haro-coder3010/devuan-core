# Instalar herramientas en el Host:

# Detectar discos:
lsblk

# Eliminar firmas y GPT residual (Reemplazar sdX por el disco real, ej: sda)
sudo wipefs -a /dev/sdX
sudo gdisk --zap-all /dev/sdX

# Crear GPT limpia:
sudo parted /dev/sdX mklabel gpt

# PARTICIONADO OFICIAL (Fiel a v2.0, sin /boot separada para asegurar compatibilidad):
# /dev/sdX1 -> EFI   -> FAT32 -> 512 MB
# /dev/sdX3 -> ROOT  -> EXT4  -> Resto del disco

sudo parted /dev/sdX mkpart ESP fat32 1MiB 513MiB
sudo parted /dev/sdX set 1 esp on
sudo parted /dev/sdX mkpart ROOT ext4 513MiB 100%

Justificación Técnica para la Documentación (Versión 2.1)
Por qué configurar crypttab antes del Kernel:
"En la arquitectura Devuan Core 2.0, el kernel se consolidaba antes de mapear la identidad de los discos.
Aunque update-initramfs finalizaba exitosamente en el chroot, generaba un ramdisk genérico ('ciego').
Esto obligaba a realizar una regeneración manual del initramfs al final de la instalación para que el sistema 
pudiera detectar el contenedor LUKS en el arranque real. En la versión 2.1, se adelanta la configuración de /etc/crypttab. 
Al inyectar el UUID del contenedor cifrado de forma temprana, cuando el instalador de APT invoca a update-initramfs, 
el script lee nativamente la topología de almacenamiento y compila una imagen initramfs que ya incluye los módulos 
criptográficos (cryptsetup) y la instrucción de pedir la contraseña de descifrado desde el primer segundo del booteo, 
logrando un despliegue más limpio, automatizado y sin pasos redundantes al final."

RESUMEN EJECUTIVO
=================

Tras finalizar la construcción completa de Devuan Core 2.1 con
partición raíz cifrada mediante LUKS, el sistema no aparecía en el
menú de arranque UEFI.

El síntoma inicial sugería una instalación incompleta o corrupta.

La auditoría posterior demostró que:

* Devuan estaba correctamente instalado.
* El kernel existía.
* El initramfs existía.
* LUKS funcionaba correctamente.
* OpenRC estaba instalado.
* La raíz del sistema era funcional.

El problema real se encontraba exclusivamente en la capa EFI/GRUB.

====================================================================
INCIDENTE #1
ESTRATEGIA "DELEGAR GRUB AL HOST"
=================================

HIPÓTESIS ORIGINAL

La versión inicial de Devuan Core 2.1 asumía que:

1. Devuan se instalaría dentro de LUKS.
2. El sistema anfitrión (AntiX) ejecutaría update-grub.
3. os-prober detectaría automáticamente Devuan.
4. El firmware arrancaría Devuan mediante la entrada generada.

RESULTADO REAL

El comando:

update-grub

generó únicamente entradas para AntiX.

No apareció ninguna referencia a Devuan.

SALIDA OBSERVADA

Found linux image: /boot/vmlinuz-6.6.119-antix...
Found initrd image: /boot/initrd.img...

No apareció ninguna línea:

Found Devuan GNU/Linux

INVESTIGACIÓN

Se abrió el contenedor LUKS manualmente:

cryptsetup open /dev/sda3 cryptroot

Posteriormente:

mount /dev/mapper/cryptroot /mnt

Auditoría:

ls /mnt

Resultado:

Sistema completo presente.

Auditoría de kernel:

ls /mnt/boot

Resultado:

vmlinuz-6.12.90+deb13.1-amd64
initrd.img-6.12.90+deb13.1-amd64

Kernel presente.

Initramfs presente.

Sistema operativo válido.

CAUSA RAÍZ

os-prober no detecta instalaciones LUKS que no posean un cargador EFI
propio instalado.

Devuan jamás había instalado GRUB.

CONCLUSIÓN

La estrategia:

"Delegar GRUB al Host"

NO es válida para instalaciones:

EFI + LUKS + Devuan

CORRECCIÓN CERTIFICADA

Instalar GRUB dentro del chroot.
